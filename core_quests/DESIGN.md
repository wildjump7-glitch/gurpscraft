# core_quests/DESIGN.md
Intent Broadcasting Layer for the ALife System

---

## 1. Purpose

`core_quests` is the intent‑generation layer of the ALife system.  
It does not move actors, perform pathfinding, or simulate world politics.  
Its sole purpose is to translate world‑state changes into **objectives** and broadcast them to actors through **quest nodes**.

`core_quests` sits between the strategic simulation (core_simulation + core_factions) and the autonomous actor layer (core_actors).

---

## 2. Responsibilities

### High‑level responsibilities
- Manage quest nodes (POI‑bound or region‑bound logic units)
- Generate objectives based on:
  - POI events
  - Territory changes
  - Squad conflicts
  - Faction priorities
  - Player presence
  - Simulation ticks
- Broadcast objectives to actors in the same region
- Filter objectives by faction tags
- Track objective lifecycle
- Provide APIs for objective assignment and progress reporting

### Non‑responsibilities
`core_quests` does **not**:
- Move actors
- Perform pathfinding
- Spawn entities
- Resolve combat
- Modify faction influence or territory
- Simulate squads or regions
- Render UI

---

## 3. Quest Nodes

### 3.1 Definition
Quest nodes are invisible logic units attached to:
- POIs
- Regions
- World positions
- Dynamic event sources

Quest nodes:
- Register with `core_simulation`
- Subscribe to simulation events
- Update on simulation ticks
- Generate objectives
- Broadcast objectives to actors in the same region
- Filter objectives by faction tags
- Maintain internal state (cooldowns, last update tick, etc.)

### 3.2 Registration
Quest nodes must register with:
- `core_simulation.register_poi` (if POI‑bound)
- `core_simulation.on_tick`
- `core_simulation.registercallback(event_name, fn)`

---

## 4. Objective Model

### 4.1 Objective Schema
```lua
{
  id = "string",
  type = "goto" | "investigate" | "interact" | "patrol" | "flee",
  target = {
    pos = {x, y, z} OR
    entity_id = string OR
    area_id = string
  },
  radius = number,
  priority = number,
  faction_tags = { "string", ... },
}
```

### 4.2 Objective Lifecycle
- Created — generated by a quest node
- Broadcast — sent to actors in the region
- Accepted — actor converts to internal goal
- In Progress — actor is moving/executing
- Completed — actor reports success
- Failed/Expired — actor abandons or node invalidates

### 4.3 Faction Filtering
Objectives may include `faction_tags` to restrict:
- Which actors may accept them
- How factions prioritize them
- Whether they override existing goals

---

## 5. Integration with core_simulation

### 5.1 Region Grid Awareness
Quest nodes must use:
- `core_simulation.world_to_region(x, z)`
- `core_simulation.region_to_world_bounds(rx, rz)`

Objectives are broadcast **per region**, not per node.

### 5.2 POI Integration
Quest nodes may:
- Register as POIs
- Update POI alert levels
- React to POI ownership changes

### 5.3 Event Integration
Quest nodes must subscribe to:
- `onterritorychanged`
- `onpoicaptured`
- `onregionconflict`
- `onsquadcreated`
- `onsquaddestroyed`

Quest nodes generate objectives in response to these events.

### 5.4 Tick Integration
Quest nodes may perform periodic updates via:
- `core_simulation.on_tick(callback)`

Tick‑driven logic includes:
- Cooldown expiration
- Objective regeneration
- POI alert decay
- Region‑based scanning

---

## 6. Public API

### 6.1 Quest Node Registration
- `core_quests.register_quest_node(def)`
- `core_quests.unregister_quest_node(node_id)`
- `core_quests.get_quest_node(id)`

### 6.2 Objective Querying
- `core_quests.get_objective(id)`
- `core_quests.get_objectives_in_region(rx, rz)`
- `core_quests.report_progress(actor_id, objective_id, status)`

### 6.3 Event Consumption
- `core_quests.subscribe(event_name, fn)`
- `core_quests.unsubscribe(event_name, fn)`

## 7. Integration with core_factions

`core_quests` must incorporate faction strategy into objective generation.

### 6.1 Faction Priority Modifiers
Quest nodes must query faction data to adjust:
- Objective priority
- Objective type selection
- Broadcast radius
- Actor acceptance rules

### 6.2 Faction Tags
Objectives may include faction tags to:
- Restrict which actors may accept them
- Bias objectives toward specific factions
- Prevent cross‑faction contamination

### 6.3 Territory‑Aware Intent
Quest nodes must consider:
- Region ownership
- Contested states
- Influence levels
- Faction hostility relationships

---

## 7. Integration with core_actors

`core_quests` does not move actors.  
It only provides **intent**.

### 7.1 Objective Broadcasting
Quest nodes broadcast objectives to actors in the same region via:
- `core_actors.assign_objective(actor_id, objective)`
- `core_actors.broadcast_objective(faction_id, objective)`

### 7.2 Progress Reporting
Actors may report progress via:
- `core_quests.report_progress(actor_id, objective_id, status)`

### 7.3 Actor Filtering
Quest nodes must filter actors by:
- Faction tags
- Actor type
- Actor state (idle, busy, blocked)

---

## 8. Objective Generation Patterns

Quest nodes may generate objectives based on:

### 8.1 POI Events
- POI captured
- POI under attack
- POI alert level rising

### 8.2 Territory Events
- Region contested
- Region ownership changed
- Influence threshold crossed

### 8.3 Squad Events
- Squad enters region
- Squad destroyed
- Squad conflict detected

### 8.4 Player Presence
- Player enters region
- Player interacts with POI
- Player triggers anomaly or hazard

### 8.5 Periodic Updates
- Patrol routes
- Investigation cycles
- Reinforcement requests

---

## 9. Example Objective Types

### 9.1 Investigate Region
Triggered when:
- Region becomes contested
- POI alert level rises

### 9.2 Reinforce POI
Triggered when:
- Friendly POI is under threat
- Enemy squad enters region

### 9.3 Scout Territory
Triggered when:
- Faction expansion logic requests intel
- Region influence is low or unknown

### 9.4 Patrol Route
Triggered on:
- Tick‑based patrol cycles
- Faction security policies

---

## 10. Completion Criteria

`core_quests` is functioning correctly when:

1. Quest nodes register with core_simulation  
2. Quest nodes react to simulation events  
3. Objectives are generated based on world‑state  
4. Objectives are broadcast region‑wide  
5. Actors receive and accept objectives  
6. Faction tags influence objective distribution  
7. Tick‑driven updates regenerate or expire objectives  
8. The ALife feedback loop is maintained
